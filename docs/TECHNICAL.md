# AULA L99 screen – technical notes

Everything here was worked out by static analysis of the screen firmware (HFD_Code V2.3) and the UI file, plus tests on a real keyboard. Addresses are for those exact versions.

## Hardware (what's known)
- Two USB devices inside the keyboard:
  - Keyboard MCU (SONiX VID 0C45, PID 800A on cable; 05AC:024F via 2.4G dongle). Vendor channel = interface 3, 64-byte HID feature reports.
  - Screen module EEEF:268A, a USB serial (CDC) device, 115200 8N1. Packets start `5A A5`, CRC16.
- Screen chip: Levetop UartTFT-II family, most likely LT168B (community claim) with 128 MB NAND (W25N01GV). It has its own MCU running AULA's `HFD_Code_V2.x.bin` (not encrypted; CPU is Motorola M*Core-compatible little-endian, 16-bit instructions — probably a C*Core/C-SKY ABIv1 core — loaded at 0x60010000, RAM 0x800000–0x875000, reset 0x60017490, main ≈ 0x600449B0; disassemble with binutils objdump `-m mcore -EL`, whose backward conditional branches are off by 0x800). "HFD" ≈ 华奋达, the screen-module maker.
- The screen updater flashes two parts: `HFD_Code_V2.x.bin` (screen firmware) and `UartTFT-II_Flash.bin` (127 MB UI image: pictures, fonts, pages).
- Screen download (upgrade) mode: hold Fn + Space for about 5 seconds; do the same again after flashing to leave it.

## UI image format (UartTFT-II_Flash.bin)
- Image table at 0x622A84: 12-byte records (u32 addr, u16 w, u16 h, u32 format<<24|length).
- **Format 2 = ARGB4444** (top nibble = alpha; 0x0FFF = transparent white). Format 0 = plain RGB565. (Reading it as RGB565 with a cyan colour key gives cyan fringes. `tools/l99_assets.py` round-trips the 16-bit values exactly; new art should be encoded with `tools/argb4444.py`.)
- Full-screen pages use "LT" palette+RLE resources (`tools/lt_encode.py` encodes/decodes them). Chinese text uses a 20 px 2-bit GB2312 font (4 copies).

## Pages, touch areas and the screen's command set (decoded 2026-10-17)
- The screen runs Levetop's standard UartTFT-II engine. AULA's uploads are the standard "Write SPI Flash" (0x64) / "Verify" (0x66) commands from the UI_Editor-II manual ch. 12. Standard commands: read 0x03 / write 0x10, CRC16-Modbus over cmd+addr+data, low byte first. Registers: 0x7000 (aliased to 0x2000 in this firmware) page, +1 backlight (0–63), +2..+7 time, +0x3F language.
- UI image header (offset 0): table of (u32 addr, u32 count). Page table at 0x21DD0: 30 pages × 2 entries (u32 addr, u16 len) = display-widget block + touch-widget block. Page backgrounds at 0x5C008E: 12-byte records (u32 addr, u16 w, u16 h, u32 len|fmt<<24; fmt 16 = none, 1 = raw RGB565, 3 = LT palette-RLE).
- Touch Button record (19 bytes): 01, flags (0x80; 0xC0 = report value), 0x10, x1, y1, x2, y2, returnValue, unpressedIcon, pressedIcon, pageGoto (u16 LE each; 0xFFFF = none).
- Page map: 0 clock, 1 home, 4 settings (5–15 sub-pages), 16 screen custom., 17 colour, 18 play/media (reports 0x20–0x24), 19 real-time data, 20 photo frame, 21 Mini Numpad (reports 0x30–0x40), 22 calculator, 23 touchpad. Pages 24 and 29 are completely empty. The home menu has two free grid slots (row 3) – the mod uses both.
- Screen USB serial port only answers the flash-command format: `5A A5 00 <len BE16 = body+2> <cmd> <addr BE32> <payload> <CRC16-Modbus over cmd..payload, low byte first>`. 0x64 write, 0x65 read, 0x66 verify. This general CRC rule reproduces all 154 captured upload packets (it replaces gavindi's per-length CRC table). No touch reports arrive on this port.
- Reported values go to the keyboard's chip, which turns known ones into PC keys (probe 2): 0x30–0x40 → numpad keys (0x30 NumLock … 0x3E Enter, 0x3F 0, 0x40 .), 0x20 prev track, 0x21 next (assumed), 0x22 vol−, 0x23 mute, 0x24 vol+ (consumer usages B6/–/EA/E2/E9 on 0C45:800A interface 1); the Play page's play/pause variable button → CD. Nothing arrives on the screen's serial port. Flash read (0x65) got no reply either.
- Uploads: the address is NOT restricted (0x04120000 accepted), but the screen silently ignores an upload whose first chunk doesn't start with a valid 11-byte picture header (u32 size, u16 w, u16 h, 0, CRC16 of pixels). The mod therefore stores the Deck picture as a fake 320x480 picture in slot 0x04120000: [header][5 pad][LT 120,000 B][zeros]; the page-30 background points at 0x04120010. `l99_deck.py --upload` rewrites it over USB.
- Page read over USB CONFIRMED on hardware: `5A A5 07 03 20 00 00 01 AA 00` → `5A A5 09 03 20 00 00 01 00 1E …` (page 30); backlight 0x2001 = 0x3F. The Deck PC app holds back each numpad key, reads the page, runs the tile action on page 30, otherwise re-sends the key unchanged. The COM port is opened only on demand and closed after 3 s idle.
- Screen firmware (static analysis): USB CDC handler at 0x600428F2 (dispatcher 0x60041E14). 0x64 writes: addr < 0x04000000 dropped silently; a picture upload must START at one of 6 slots 0x04000000/0x04060000/0x040C0000/0x04120000/0x04180000/0x041E0000 with a valid picture header (0x600403F8), or at 0x04240000 (GIF, no header check); any other addr ≥ 0x04000000 is a continuation chunk whose own address is IGNORED (data goes to start + running offset). Only long cmds 0x64/0x66/0x67; 0x65 not implemented. Short frames DO work on USB: 0x03 read replies (valid CRC needed); 0x10 write works but gives NO reply (config byte 0x8A = 0x02 disables ACK). Registers are at 0x2000 here (0x2000 page, 0x2001 backlight 0–63, 0x2002… time), not 0x7000. Page jump from PC: 5A A5 07 10 20 00 00 PP CRC (untested). Background loader (0x60037190) uses full 32-bit addresses (no 16 MB limit) but only draws fmt 0 (raw RGB565) and fmt 3 (LT RLE); fmt 16 = fill; fmt 1 draws nothing.
- The image holds 4 more UI copies with identical headers (bases 0x5B10000, 0x65455EC, 0x6F7ABD8); header addresses are relative to each copy's base. The device uses copy 0.

## Weather / clock / PC stats
- Already supported by the screen's "Real-time Data" page. Data rides in the keyboard HID "clock" packet (opcode 0x28): bytes 13–21 = CPU load, CPU temp, GPU load, GPU temp, air temp, day high, night low, condition (0 cloudy, 1 clear, 2 light snow, 3 thunder, 4 rain, 5 heavy snow), humidity.
- AULA's driver gets weather from a Chinese site (api.ip138.com), so it's useless outside China. `tools/l99_weather.py` sends Open-Meteo weather instead.
- Temperatures are unsigned on the screen: negatives display as garbage → clamp to 0 until the firmware is patched.

## Community work to build on
- github.com/gavindi/Aula_L99_Linux – full protocol notes (keyboard + screen serial upload, background/photo/GIF slots at 0x04180000 / 0x041E0000 / 0x04240000).
- github.com/Salamor/aula-l99-open-widgets – good vision, no code yet; issues contain the LT168B findings. Its README's JPEG protocol (`12 34 56 78`) is WRONG for the L99: checked its own captures — that traffic goes to USB device 87ad:70db (another display on that PC). The L99 screen (eeef:268a) got 154 `5A A5` packets writing raw RGB565 320x480 to 0x041E0000 (photo-frame slot), matching gavindi.

## What the mod changes (`tools/build_l99.py`)
- **Languages are built into the screen firmware.** Every picture is looked up as `language × 569 + number` (draw_icon 0x600349F8 and ~60 other sites use 0x812BD3 × header[0x34]). Language count = UI config byte 0xC1 (= 2 in AULA's file); language table at header 0x50 (2 entries × (addr,len) of variable records, both empty). Settings > Language writes register 0x203F → firmware loads table entry, sets 0x812BD3, redraws. AULA's file only filled language 0, so "Chinese" points past the table. The builder moves the picture table to 0xB20000; with `--bilingual` it holds 1138 entries (two languages of 569) so a second UI language can be switched at runtime.
- At boot 0x812BD3 = 0 although register 0x203F is restored from settings; with deck.json `"keep_language": true` the PC app writes 0x203F back every 30 s.
- Backgrounds (page_goto) are NOT per language; anything with words is a picture.
- **Hidden game = Tetris on page 24**, enabled when the UI version number in the config block is odd (`0x870430 & 1` → 0x812C59). Version "V2.20" at config+48 (0xB0); config block 0x80..0x173 is protected by CRC32 (zero start, no final xor, firmware table 0x60010100) over the block with bytes +0xEC..+0xF3 replaced by `68 45 71 19 88 96 77 23`; stored as ~crc, crc at +0xEC/+0xF0. The mod sets "V2.21" and re-signs.
- Tetris: board 10×23 cells of 20 px at (3,11)-(202,470), next piece (208,11)-(307,110), drawn by firmware with fill_rect. Input: touch buttons (type C001) with values 0x50 W rotate, 0x51 S down, 0x52 A left, 0x53 D right, 0x54 space pause/start, 0x55 new game → calc_key_decode → 0x812C58 → main loop (game tick when page 24). These values are not sent to the keyboard MCU. Score = u64 BE in vars 0x254–0x257 (+10 per line), level var 0x328 (score/50, max 3), "Game Over !!!" written to var 0x258. Leaving page 24 resets the game.
- Display widget formats (decoded): 03 static/var picture = var,x,y,icon_first,icon_last(FFFF=static),vmin,vmax. 04 number = var, type (0 u8,1 u16,2 u32,0x80+ signed), x, y, int digits, dec digits, flags (2 = right-aligned: x is the RIGHT edge), first digit pic, last digit pic. 01 text = var, max bytes, x1,y1,x2,y2, font w,h, font lib (2 = 32 px, 3 = 20 px; table at header 0x10), 0, align (0 left 1 centre 2 right), colour RGB565 (3 bytes), bg (3 bytes), flags.
- Variable writes over USB: `5A A5 len 10 aH aL data… CRC16` (no reply), var RAM 0x80E5C8 + 2×var, vars 0x0000–0x1FFF plain. Initial values from flash header[0] (0x11DD0, 0x41FE bytes).
- **Live page = page 31** ("Live" button on the Deck page, top right): text vars 0x1000 (32 px), 0x1010–0x1070 (20 px), filled by `l99_live.py` inside the Deck runner while the page is open. The screen fonts are ASCII only.
- Free picture slots used: 440 score, 441 level, 442 Live title, 443–445 card labels, 446–459 Tetris buttons (normal/pressed). Slots 436–499 are empty in AULA's file.
- Home: new icons drawn into sprite 0, new buttons Deck (163,270) and Game (237,270).
